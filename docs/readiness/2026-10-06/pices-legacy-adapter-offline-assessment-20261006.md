## Real remaining publication gap

`publish_records.py` accepts a same-ID, QA-matching `state='done'` record and tests only `metadata.communities` for `identifier='pices'`. It correctly records that as **reported** or **unconfirmed**, but the generated report nevertheless says a 100% successful publication rate means records should be visible in PICES. Neither the requested legacy community label nor publication proves accepted membership. Evidence: `scripts/publish_records.py:89,254,309,482`.

The maintained modern path binds actual PICES authority, validates request receiver/topic/owner, attaches the review before submission, and requires accepted request plus a five-GET published fence with exact membership UUIDs/default and absent review before `release_complete:true`. It also preserves IDs/DOIs and treats pending as incomplete. Evidence: `scripts/modern_publication.py:82,280,635,677`; `docs/adr/0009-community-first-modern-publication.md`; `tests/test_modern_publication.py:274,423,481`.

Thus the current legacy publisher is **not sufficient for this user's community-first completion requirement**. Merely changing its report would not prevent personal-only publication. Keep it outside the first-record dispatch path; no legacy endpoint substitution, direct-publish fallback, new acceptance action or second publication implementation is warranted by this audit.
